세부 구현사항 1

출퇴근 기록과 위치 검증 흐름

  • 출근 기록은 근무지 반경 밖에서 요청되면 등록되지 않도록 처리했습니다.
  • 퇴근 기록은 반경 밖에서 요청되어도 바로 삭제하지 않고 우선 기록으로 남겼습니다.
  • 대신 해당 기록은 검토 필요 상태로 분리했습니다.
  • 고용주 확인을 거친 기록만 급여 확인과 미리받기 계산에 반영되도록 했습니다.

문제 해결 관점

  • 무조건 차단하면 실제 근무 기록이 사라질 수 있었습니다.
  • 무조건 반영하면 부정확한 기록이 급여 확인과 미리받기 계산에 포함될 수 있었습니다.
  • 따라서 기록 보존과 계산 반영 기준을 분리했습니다.
}

세부 구현사항 2

급여 계산 기준 스냅샷

  • 월간 출퇴근 기록을 기준으로 급여 확인 결과를 생성했습니다.
  • 실제 입금액과 예상 급여 차이를 급여 확인 시점의 스냅샷으로 저장했습니다.
  • 이후 문서 생성과 문제 제기 준비에서 같은 급여 확인 결과를 참조하도록 했습니다.

증빙 문서 / 문제 제기 기준 연결

  • 증빙 문서와 문제 제기 자료를 만들 때, 해당 급여 확인 결과가 사용자의 것인지 확인했습니다.
  • 문제 제기 준비 화면에서도 같은 급여 확인 결과를 재사용했습니다.
  • 문서 생성 흐름에서는 중복 요청 처리 근거가 확인되어, 해당 범위로만 표현합니다.
}

검토·승인 흐름과 테스트 보강

고용주 등록과 검토 흐름

  • 고용주가 발급한 등록 코드를 근로자가 입력해 회사/사업장에 연결되는 흐름을 구현했습니다.
  • 근로자와 회사/사업장 연결 정보를 만들고, 검토가 필요한 기록을 고용주가 확인할 수 있는 목록으로 구성했습니다.
  • 고용주 확인 후 ‘검토 필요’ 기록을 ‘계산 반영’ 상태로 전환했습니다.

미리받기 관리자 승인

  • 관리자가 미리받기 요청을 승인할 수 있는 API를 구현했습니다.
  • 인정된 근무 시간이 미리받기 가능 여부 계산에 반영되는지 회귀 테스트를 보강했습니다.
  • 개인 기여는 관리자 승인 API와 인정 시간 회귀 테스트 범위로 제한해 표현합니다.

프로젝트 회고

단순히 기록을 저장하는 것보다, 어떤 기록을 계산에 반영할 수 있는지 상태를 분리하는 것이 중요했습니다. 하나의 출퇴근 기록이 급여 확인, 증빙 문서, 문제 제기, 미리받기 판단의 기준이 되기 때문에 기준 데이터를 명확히 고정하는 경험을 했습니다.
