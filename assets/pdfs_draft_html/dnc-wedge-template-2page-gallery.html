세부 구현사항 1

외부 혈당 데이터 수집

  • 외부 혈당 측정 서비스에서 5분마다 새 혈당 기록을 가져왔습니다.
  • 인증이 만료되면 갱신 후 다시 요청하고, 가져온 데이터는 임시 저장 공간을 거쳐 DB에 저장했습니다.

사용자별 혈당 기록 분리

  • 사용자별 임시 저장 공간을 분리해 혈당 기록이 섞이지 않도록 했습니다.
  • 같은 혈당 기록이 반복 저장되지 않도록 사용자와 외부 기록 ID를 함께 확인했습니다.

센서 상태 전환

  • 연동 직후에는 센서를 대기 상태로 관리했습니다.
  • 첫 혈당 데이터가 들어오면 실제 센서 정보를 연결해 사용 가능 상태로 전환했습니다.
}

외부 혈당 데이터가 사용자 기록이 되는 흐름

외부 혈당 데이터를 그대로 저장하지 않고, 사용자별 임시 저장 공간·중복 기록 확인·센서 상태 전환 기준을 두어 서비스 기록으로 연결했습니다.

외부 혈당 측정 서비스5분마다 새 혈당 기록 제공
→
주기적 수집 작업사용자별 혈당 기록 가져오기
↓
인증 갱신 후 재요청권한 만료 시 새 인증으로 다시 호출
→
사용자별 임시 저장 공간Redis에 사용자 ID 기준으로 분리
↓
중복 기록 확인사용자와 외부 기록 ID를 함께 확인
→
DB 저장 / 센서 상태 변경혈당 저장, 대기 → 사용 가능 전환

핵심은 사용자별 저장 기준과 중복 기록 확인 기준을 명확히 한 것입니다. 실제 장애 감소 수치는 확인되지 않아 정량 성과로 쓰지 않습니다.

세부 구현사항 2

식단 분석 결과 연결

  • 식단 사진을 음식 분석 서버로 보내 음식명과 양 정보를 받았습니다.
  • 분석 결과를 음식 정보와 매칭해 식단 기록과 영양 계산에 사용할 수 있도록 변환했습니다.

예상 혈당 저장

  • 섭취량 단계를 계산 가능한 음식 양 비율로 변환했습니다.
  • 사용자 정보, 최근 혈당, 식단 정보를 조합해 예상 혈당 결과를 저장했습니다.

AI 요약과 기본 안내

  • 요약 문구가 과장되거나 없는 정보를 추정하지 않도록 출력 조건을 제한했습니다.
  • 데이터 부족이나 외부 호출 실패 시 기본 안내 문구를 보여주도록 처리했습니다.
}

AI 분석 결과를 사용자 기록으로 변환

AI 모델 성능이 아니라, 음식 분석 서버의 결과를 식단 기록·예상 혈당·요약 리포트로 연결한 백엔드 흐름에 집중했습니다.

01 식단 촬영
식단 사진 업로드
02 예상 혈당
예상 혈당 결과
03 리포트
하루 요약 리포트

백엔드 처리 흐름

앱 요청 수신식단 사진 업로드와 분석 요청 처리
이미지 저장 / 음식 분석저장소 보관 후 음식 분석 서버 호출
식단 기록 변환음식 정보 매칭, 양 보정, 예상 혈당 저장
요약 문구 생성출력 조건 제한과 실패 시 기본 안내

문제 해결과 운영 흐름

문제 해결 관점

  • 혈당 데이터는 사용자별 저장 기준과 중복 확인 기준을 두어 섞이지 않도록 처리했습니다.
  • 음식 분석 결과는 식단 기록, 영양 정보, 예상 혈당, 요약 문구로 변환했습니다.
  • 외부 호출 실패나 데이터 부족 상황에서는 기본 안내 문구를 제공하도록 처리했습니다.

인프라/협업 흐름

  • 서비스별 변경 여부를 확인한 뒤 승인 단계를 거쳐 배포하도록 구성했습니다.
  • 컨테이너 기반 배포 후 결과를 팀 채널에 공유하는 흐름 구성에 참여했습니다.
  • Backend, AI Server, Mobile이 함께 배포되는 구조에서 변경 범위와 결과 공유를 맞췄습니다.

프로젝트 회고

외부 서비스와 AI 서버를 연결할 때는 단순 호출보다 사용자별 저장 기준, 실패 시 기본 응답, 중복 방지 기준이 중요하다는 점을 배웠습니다.
