Wedge

브라우저 실행 기반 UX 진단 리포트 서비스

Run 상태 관리, Analyzer 비동기 요청, 분석 결과 기반 리포트 생성을 연결한 브라우저 실행 기반 UX 진단 서비스입니다.

✔️ 프로젝트 정보 및 구성

  • 2026.04 ~ 2026.05 · 약 7주 · 6인 · Web
  • GitHub Repository
  • 백엔드: Java 17, Spring Boot 3.5, MyBatis
  • 웹: React, Vite, TypeScript
  • 실행·분석: Node.js·Playwright Runner, FastAPI Analyzer
  • 데이터·메시징: PostgreSQL, Redis, RabbitMQ
  • 운영: Docker, NGINX, Jenkins, AWS S3

✔️ 담당 역할

  • Spring Boot 백엔드에서 Run·Runner 실행 상태를 관리했습니다.
  • Analyzer 입력 구성과 비동기 요청 흐름을 구현했습니다.
  • 분석 결과를 바탕으로 리포트 생성과 상태 반영을 구현했습니다.

✔️ 구현 사항

  • Run 생성·시작부터 Runner callback, 단계 이벤트, checkpoint·capture, 실행 실패까지 상태가 이어지도록 구성했습니다.
  • Analyzer 요청 시점의 입력값을 스냅샷으로 보관하고, 내부 API와 서명 URL로 분석에 필요한 데이터를 제공했습니다.
  • 분석 작업을 pending 상태로 생성한 뒤 Outbox·재시도 흐름으로 요청을 발행하고, callback 중복을 방어했습니다.
  • 완료된 분석 결과로 리포트를 생성하고, 같은 Run의 중복 생성 방지와 최신 리포트 상태 반영을 처리했습니다.

✔️ 문제 해결

  • 문제DB 작업은 생성됐지만 MQ 발행 실패로 분석 요청이 유실될 수 있었습니다.
  • 원인DB 저장과 메시지 발행이 분리되어 실패 추적과 재시도가 어려웠습니다.
  • 해결작업 생성과 Outbox 저장을 같은 트랜잭션으로 처리하고, eventId 중복 방어와 DLQ 실패 상태 전환을 적용했습니다.
  • 결과요청 유실 위험을 추적·재처리하고, 중복 callback과 Runner 실패를 정상적으로 상태에 반영했습니다.

✔️ 프로젝트 성과

  • 분석 요청 메시지 유실 위험을 기록·재시도 흐름으로 관리했습니다.
  • 외부 callback이 재수신되어도 상태와 결과가 중복 반영되지 않도록 방어했습니다.
  • Runner 실행 실패를 Run 실패 상태와 실패 정보로 연결해 사용자에게 노출했습니다.

✔️ 프로젝트 리뷰

  • 지금이라면 중복 callback, 완료 상태 이후 이벤트, Outbox 재시도 흐름을 테스트로 더 촘촘히 검증하겠습니다.
  • 비동기 흐름은 정상 처리뿐 아니라 재시도, 중복 방지, 실패 상태의 사용자 노출까지 함께 설계해야 한다는 점을 배웠습니다.
